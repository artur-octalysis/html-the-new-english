This is a fictional teaching project. The user's session-specific five-step process is authoritative for this presentation; it is not a claim that wider TOG process naming has been approved.

Canonical project data: `site/project/fitness-project.json`. Rendered strategy, feature list, loop labels, economy assumptions, and wireframe policy derive from it. Stable IDs connect M1 → A1 → F1/F2 → R3. Keep these references intact.

When a mechanic changes:
1. Read this file, the canonical data, and PRESENTATION.md.
2. Identify affected strategy, desired actions, metric definitions, mechanics, economy assumptions, and UI rules. Trace dependencies in both directions.
3. Propose a focused source edit and explain its rationale and uncertainty. Never invent new research, costs, validation, or approval.
4. Recompute dependent values, run model/build tests, and inspect the rendered website and wireframe.
5. Open a pull request showing the source diff and affected views. The project owner reviews intent; the economy designer reviews cost assumptions. Changing a metric definition requires baseline review.

The repository does not run AI automatically. An agent must be instructed or a workflow configured. Shared-source views update deterministically; semantic decisions require review. The presentation's impact preview is a scripted example, not an actual AI inference.

The 30% → 40% metric is an illustrative hypothesis. Power/Ease uses a workshop 1–5 scale; do not imply an approved TOG scoring formula. Reward budget math is a simplified scenario model, not a forecast. No real rewards are purchased or redeemed.
