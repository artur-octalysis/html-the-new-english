01 / THE BUSINESS CASE A hypothesis about how we work

Structure we can see.
Ideas we can try.

Visual hierarchy shows how ideas relate. Interaction shows what happens when we make a choice. Together, they give a business conversation something concrete to work with.

Structure.

Headings, grouping, spacing, and emphasis make priorities and relationships visible.

Interaction.

Change an input and see the consequence. Turn a hidden assumption into something we can question.

Shared meaning.

People across roles can point to the same element, compare interpretations, and propose a change.

From “I think I understand” to “let’s try it together.”A prototype is a conversation we can interact with.
The business case · 3 minSay: “Common language means a shared way to express and examine ideas. It does not mean everyone reads source code.” Mention a proposal with selectable scope, an explorable dashboard, an onboarding journey, or a workshop exercise. These are possible applications, not evidence of client outcomes. Explain that layout carries meaning: a headline sets priority, grouping shows relationships, and a sequence suggests a process. Interaction adds cause and effect. Visual polish alone is insufficient; a polished interface can still encode a bad assumption.

Many forms · 2 minClick each view and ask what becomes easier to see. Say: “Much of the information we exchange at work can be represented in a web experience.” Avoid claiming that all formats are based on HTML. PDF, spreadsheet, and Figma documents have their own native models. Recreating a view does not automatically preserve formulas, design constraints, accessibility, or full editing capability. The browser can also use SVG, Canvas, and other technologies alongside HTML. Our advantage is a flexible shared medium, not universal format replacement.

Try the argument · 4 minAsk the audience to suggest a feedback time, then move the slider. At six minutes, the model needs 36 minutes; at four, it needs 24. The calculation is intentionally simple. The point is shared interpretation: the vague word “enough” now has a visible consequence. Markdown is useful for the brief and rationale; the interactive view helps explore the tradeoff. A spreadsheet could also model this. HTML is useful here because the model can live alongside the explanation in the same browser experience.

Why now, and where each medium fits · 3 minSay: “My argument goes beyond writing English in Markdown files. We can also communicate through experiences people can use.” AI lowers some implementation effort, but judgment, review, accessibility, and testing still matter. “HTML” in the title is shorthand for the web toolkit: HTML structures content, CSS styles it, and JavaScript adds behavior. 05 / THE HANDOFF ADVANTAGE Give the next person something they can change

“Take this file.
Make the idea better.”

A small HTML prototype puts structure, styling, and behavior in readable source. Another person can give it to their AI, request a change, and open the result in a browser.

PDF

Useful for a stable, shareable view. Changing its logic or interactions usually means returning to the source—or reconstructing them.

Figma

Useful for collaborative visual design and design systems. AI editing depends on access and compatible tools; browser behavior may need implementation.

HTML

Useful for a working browser experience. AI can edit the source directly, and we can inspect both the change and its behavior.

TRY THIS ON ANOTHER PAIR’S FILE

“Read this HTML file and its README. Explain what the experience is trying to achieve. Add an option to observe before contributing. Preserve the visual hierarchy and existing behavior. Show me what changed and how to test it.”

Read → explain → edit → open → test. Clear context makes the next edit easier.
Show the editing advantage · 4 minUse the same shared-model HTML in another AI tool, or show a small before/after diff. The advantage is direct access to a working representation, not a claim that PDF or Figma cannot be AI-edited. PDF is a delivery format, Figma is an editable design environment, and HTML/CSS/JS is executable by the browser. Figma can support AI tools and interactions; its workflow is different. Small self-contained HTML files are particularly portable. Large apps with dependencies, assets, or backends need more context. Reading source is not the same as understanding design intent, and every AI edit still needs review.

Merges and review · 3 minSwitch to overlapping changes. Both branches changed the same button label from “Join now” to different alternatives. Git may stop with a conflict; someone decides the intended result, edits it, and records the resolution. Git does not understand our business intent. Even without a text conflict, combined changes can break behavior. Pull requests are GitHub’s review workflow, not a core Git command. Deployment is configured automation, not something Git does inherently.

Git collaboration & swap · 9 minUse the public workshop repository. Each pair can fork it, create its own prototype folder, and open a pull request. Explain the distinctions: a commit records a change; a branch isolates a line of work; a diff shows what changed; a merge combines work. GitHub pull requests add the review conversation. Git can combine compatible text changes, but overlapping edits may need human conflict resolution. A successful merge does not guarantee that behavior is correct. Our checks and review help catch problems before publishing. During the session: collect first versions via pull requests and merge before the swap. Receiving pairs start from the merged version and open a new pull request. Original authors review. Open the repository from the gallery. Each prototype lives in prototypes/your-team/, with index.html, prototype.json, and README.md. After review and merge, publishing updates the gallery.

16 / SHARED PROTOCOLS Different tools. Shared expectations.

Git keeps the history.
Our protocol keeps the intent.

BEFORE BUILDING

Make intent explicit.

Start from the latest shared version. Read the brief. Name the intended behavior and the change you want to make.

BEFORE SHARING

Check the experience.

Keep the change focused. Inspect the diff. Run the interaction and check what still works. Record uncertainty.

BEFORE MERGING

Explain the change.

Explain what changed and why. Review the result together, resolve conflicts if needed, and leave a useful handoff.

Debrief: where did you have to guess?Which shared habit would have saved you time?
Debrief · 4 minAsk each pair to name one piece of missing context and one useful piece of context. Refine these working agreements with the team. Protocol means a shared way of working here, not MCP or another technical integration standard.
